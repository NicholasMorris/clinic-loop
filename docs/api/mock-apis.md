# Mock APIs for SimClinic

The API provides FastAPI endpoints to query a frozen world snapshot from M1-1, enabling agents and dashboards to read patient, order, consult and message records without accessing live engine state.

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| GET | /patients | List all patients in the snapshot |
| GET | /patients/{patient_id} | Get a patient by ID |
| GET | /orders | List all orders in the snapshot |
| GET | /orders/{order_id} | Get an order by ID |
| GET | /consults | List all consults in the snapshot |
| GET / consults/{consult_id} | Get a consult by ID |
| GET | /messages | List all messages in the snapshot |
| GET | /messages/{message_id} | Get a message by ID (includes newly created) |
| POST | /messages | Create a new message |

## Error Responses

### 404 Not Found

Returned when a requested entity ID is not found in the snapshot.

```json
{
  "detail": "Patient P999999 not found"
}
```

### 422 Unprocessable Entity

Returned when a POST request body fails schema validation (e.g., missing required fields).

```json
{
  "detail": [
    {
      "type": "missing",
      "loc": ["body", "patient_id"],
      "msg": "Field required",
      "input": null
    }
  ]
}
```

## Snapshot Loading

The app is created by calling `create_app(snapshot_path)` with the path to a world snapshot file generated by M1-1's `write_world_snapshot()`.

### Schema Validation

On startup, `create_app()` reads the snapshot's `schema_version` field and raises `SnapshotVersionUnsupported` if it is not "1". This ensures API and snapshot format remain in sync.

```python
from clinicloop.api.app import create_app, SnapshotVersionUnsupported

try:
    app = create_app(snapshot_path="world.json")
except SnapshotVersionUnsupported as e:
    print(f"Error: {e}")
```

## Determinism

Two app instances created from the same snapshot file will return byte-identical response bodies for all GET endpoints. This allows integration tests to compare responses exactly, and enables the dashboard and any other consumers to reload from the same snapshot and get consistent results.

## Collection Endpoints

Collection endpoints (GET /patients, /orders, /consults, /messages) return the complete array of all entities in the snapshot. Pagination and filtering are not implemented; clients should filter and paginate in memory if needed. This is intentional: the snapshot is frozen and typically small (test world: ~5 patients, ~5 orders, ~5 consults, ~2 messages).

## Message Creation

POST /messages accepts a `MessageCreate` body and returns 201 with a newly created message. The new message is stored in the app's request state and is retrievable via GET /messages/{message_id}. However, newly created messages do **not** appear in GET /messages (which returns only snapshot messages). This preserves the frozen-snapshot semantics: the collection endpoint shows the deterministic baseline, while individual-record endpoints support transient write operations for agent use.

## Loopback-Only Binding

The API binds to loopback addresses only (127.0.0.1, ::1, or localhost) to enforce local-only constraint and enable testing under pytest-socket with loopback restriction. Creating an app with a non-loopback host raises ValueError.

```python
from clinicloop.api.app import create_app

try:
    app = create_app(snapshot_path="world.json", host="0.0.0.0")
except ValueError as e:
    print(f"Error: {e}")  # "Host must be loopback..."
```

## Future: Outbound Guard Boundary

M2-4 will add an outbound guard boundary to POST /messages that enforces the triage guard rules and returns 422 with a rule_id if any rule is violated. The request/response signatures will remain compatible.

## OpenAPI Documentation

The API publishes an OpenAPI 3.0 document at GET /openapi.json, listing all resource paths and schemas for code generation and introspection.
